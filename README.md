# AI Return-Risk Scorer (Razorpay Mock Project)

> 🎥 **Buildathon Pitch Video:** [Watch the 5-Minute Pitch on Google Drive](PASTE_YOUR_GOOGLE_DRIVE_LINK_HERE)

An end-to-end Machine Learning and Rule-Based system designed to predict and mitigate **Return-To-Origin (RTO)** and **Return-to-Vendor (RTV)** risks for e-commerce transactions. 

This project simulates a production-grade scoring pipeline that dynamically routes users to a Rule Engine (for new users/cold starts) or a Machine Learning model (for returning users) to assign a risk score and an actionable decision (ALLOW, VERIFY_OTP, MANDATE_PREPAID, BLOCK).

---

## Key MLOps & Data Science Features

This project isn't just a basic `model.predict()` script. It includes advanced data science practices tailored for business profitability:

1. **Custom FPC-Optimal Thresholding**: Instead of relying on a default `0.5` probability threshold or optimizing purely for PR-AUC, the pipeline dynamically sweeps thresholds to minimize actual business costs (e.g., False Positives cost ₹350 in lost margin, False Negatives cost ₹1200 in shipping/RTO fees).
2. **Model Comparison Suite**: A dedicated cross-validation pipeline comparing `RandomForest`, `XGBoost`, `LightGBM`, `Gradient Boosting`, and `Logistic Regression` to empirically justify model selection.
3. **Class Imbalance Strategy**: Tested both `SMOTE` (Synthetic Minority Oversampling) and `class_weight='balanced'`. The data proves that `SMOTE` generates noisy false positives in this specific domain, justifying the use of cost-sensitive learning over synthetic data generation.
4. **Feature Selection Analysis**: Utilizes **Mutual Information** and **Permutation Importance** to mathematically prove which features drive risk (e.g., `return_history_rate`) and which features add noise (e.g., `account_age_days`), preventing overfitting.
5. **Model Explainability (XAI)**: Integrates **SHAP** (SHapley Additive exPlanations) to provide human-readable reasons for every risk score in the UI.

## Project Structure & File Index

The repository is modularized into distinct layers: Data, ML Pipeline, Backend API, and Frontend.

### 1. Root Files
- `README.md`: This file. Comprehensive documentation of the project.
- `requirements.txt`: Python dependencies for the backend and ML pipeline (includes FastAPI, Scikit-Learn, XGBoost, LightGBM, SHAP, etc.).
- `docker-compose.yml`: Orchestrates the entire application (Backend + Frontend) using Docker containers for easy deployment.
- `Dockerfile.api`: Docker configuration for the FastAPI backend.
- `Dockerfile.frontend`: Docker configuration for the Vue.js frontend (uses NGINX to serve static files).

### 2. `data/` (Data Storage)
- `raw/synthetic_razorpay_data.csv`: The raw dataset generated by our simulation script. Represents 50,000 mock transactions.
- `processed/`: Contains the cleaned `train.csv` and `test.csv` used for ML training.
- `processed/plots/`: Contains generated visualizations (Correlation Heatmaps, Precision-Recall curves, Feature Importance, Model Comparison charts).
- `reference/disposable_email_domains.txt`: A text file containing a list of temporary/throwaway email domains used by the Rule Engine to flag high-risk anonymous users.

### 3. `src/ml_pipeline/` (Machine Learning Core)
This directory handles data generation, feature engineering, model training, and advanced evaluation.
- `config.py`: Centralized configuration. Defines feature lists, model hyperparameters, rule weights, and business costs (FP/FN costs).
- `generate_data.py`: A highly realistic synthetic data generator. Creates 50,000 rows of e-commerce data mirroring Indian market behaviors (high COD rates, geo-mismatch spoofing).
- `feature_engineer.py`: Cleans raw data, handles missing values, clips outliers using IQR, and safely splits data into Train/Test sets using chronological logic to prevent data leakage.
- `train_model.py`: Trains the `RandomForestClassifier`. Calculates the FPC-optimal threshold, generates the SHAP explainer, and saves the `.pkl` artifacts.
- `evaluate_model.py`: Generates comprehensive evaluation metrics, including Confusion Matrices, Risk Distributions, Correlation Heatmaps, and Permutation Importance analysis.
- `model_comparison.py`: Runs a Stratified 5-Fold Cross Validation comparing multiple algorithms (LightGBM, XGBoost, etc.) to empirically prove the best model for this specific business problem.

### 4. `src/api/` (Backend - FastAPI)
The serving layer that exposes the ML model and Rule Engine via RESTful APIs.
- `main.py`: The FastAPI application entry point. Configures CORS and mounts routers.
- `routers/evaluate.py`: The core endpoint (`POST /api/evaluate`). Takes a transaction payload, **routes new users (0 past orders) to the Rule Engine** and **returning users to the ML Model**, and returns the final risk decision.
- `routers/health.py`: A simple `GET /api/health` endpoint for Kubernetes/Docker health checks.
- `services/ml_scorer.py`: Loads the `.pkl` ML model and SHAP explainer into memory. Builds the feature vector and executes `model.predict_proba()`. Generates human-readable SHAP explanations.
- `services/rule_engine.py`: A deterministic scoring engine. Uses hardcoded business logic (e.g., checking if billing vs shipping distance > 1000km, or if the email is disposable) to score users without historical data.
- `services/geo_utils.py`: Contains the Haversine formula to calculate the geographical distance between billing and shipping pin-codes.
- `schemas/transaction.py`: Pydantic models defining the expected input JSON structure and data validation rules.
- `schemas/response.py`: Pydantic models defining the output JSON structure (Risk Score, Action, and Reasons).
- `models/`: The directory where `train_model.py` saves `random_forest.pkl` and `shap_explainer.pkl` for the API to load.

### 5. `src/frontend/` (Frontend - Vue.js)
A modern, glassmorphism-styled dashboard to test the API and visualize risk. 
- `package.json`: Node.js dependencies for the Vue 3 + Vite project.
- `vite.config.js`: Configuration for the Vite bundler (includes proxy settings to route `/api` calls to the FastAPI backend during local dev).
- `src/main.js`: Vue application entry point.
- `src/App.vue`: The main layout component. Houses the grid structure for the dashboard.
- `src/assets/styles.css`: Contains custom CSS variables, glassmorphism effects, and animations. (No Tailwind; pure CSS for maximum control).
- `src/components/JsonInput.vue`: A code-editor-like component where the user can paste or edit the transaction JSON payload.
- `src/components/RiskGauge.vue`: A dynamic, animated SVG speedometer that visually represents the 0-100% risk score returned by the API.
- `src/components/ShapWaterfall.vue`: Renders the SHAP "reasons" (positive/negative feature contributions) as a list of animated cards, explaining *why* the score was given.
- `src/components/HistoryTable.vue`: A data table that logs all evaluated transactions in the current session, showing the final action (ALLOW, BLOCK, etc.) with color-coded badges.
- `src/services/api.js`: Axios wrapper to handle HTTP communication with the FastAPI backend.

### 6. `tests/` (Quality Assurance)
- `test_api_endpoints.py`: `pytest` suite that verifies API functionality. Tests the health check, the root fallback endpoint, and sends mock payloads to `/api/evaluate` to ensure the ML/Rule routing logic works flawlessly.

## How to Run

### Option 1: Using Docker (Recommended)
This requires Docker and Docker Compose installed on your machine.
1. Build and start the containers:
   ```bash
   docker-compose up --build
   ```
2. Open your browser and navigate to `http://localhost:8080` to view the frontend dashboard.
3. The API will be running on `http://localhost:8000`.

### Option 2: Local Development (Manual)
1. **Setup Python Backend:**
   ```bash
   python -m venv venv
   source venv/bin/activate  # On Windows: venv\Scripts\activate
   pip install -r requirements.txt
   ```
2. **Train the ML Model:**
   ```bash
   python src/ml_pipeline/generate_data.py
   python src/ml_pipeline/feature_engineer.py
   python src/ml_pipeline/train_model.py
   ```
3. **Run the API:**
   ```bash
   uvicorn src.api.main:app --reload --port 8000
   ```
4. **Run the Frontend:**
   ```bash
   cd src/frontend
   npm install
   npm run dev
   ```
5. Navigate to the local URL provided by Vite (usually `http://localhost:5173`).

## Engineering & Business Rationale

### 1. Why Random Forest over LightGBM?
Our `model_comparison.py` script ran a 5-Fold Stratified CV across 5 algorithms. **LightGBM** achieved the highest PR-AUC (0.5875), narrowly beating **Random Forest** (0.5840). However, we deployed Random Forest because:
- **Simplicity vs. Marginal Gain**: A 0.0035 difference in PR-AUC yielded almost identical business cost savings. Adding an external C++ dependency (LightGBM) to the serving layer wasn't justified by the ROI.
- **Overfitting Risk**: LightGBM grows trees leaf-wise, which is prone to overfitting on smaller, synthetic tabular datasets compared to Random Forest's level-wise growth.
- **Native Ecosystem**: Random Forest integrates seamlessly with `scikit-learn` and SHAP without requiring compiled binaries in the Docker container.

### 2. Why not use SMOTE for Class Imbalance?
We tested handling our 80-20 class imbalance using both `class_weight='balanced'` and **SMOTE**. 
- SMOTE degraded our PR-AUC to 0.5082 and increased False Positives significantly. 
- **Reason**: SMOTE interpolates between minority examples. In fraud/risk detection, interpolating between two distinct fraud profiles often creates "synthetic noise" that looks like legitimate users, confusing the model. 
- We opted for cost-sensitive learning (`class_weight`) to penalize minority class errors without polluting the feature space.

### 3. Why not Deep Learning?
In e-commerce fraud, interpretability and latency are paramount. 
- **Tree-based models** handle non-linear relationships in tabular data efficiently.
- **SHAP Integration** allows merchants to see exactly *why* an order was blocked, a legal/business requirement that black-box Deep Learning struggles to fulfill. 
- **Rule Engine Fallback**: By explicitly separating users with `total_past_orders == 0` and routing them to a deterministic Rule Engine, we elegantly solve the "Cold Start" problem.

## Future Scope & Production Roadmap

While this MVP successfully demonstrates core ML logic, threshold optimization, and API structure, deploying to Razorpay's scale (thousands of TPS) requires addressing the following architectural realities:

### 1. Adversarial Data & Continuous Learning
- **Current Limitation:** Because proprietary Razorpay data is inaccessible, the synthetic dataset relies on hardcoded heuristics (e.g., Geo-mismatch + Disposable Email = Fraud). The model currently learns injected bias rather than discovering novel patterns.
- **Production Upgrade:** In a live environment, fraud is highly adversarial. The model will ingest genuine, unpredictable transactional behavior. A **Champion-Challenger (A/B testing)** deployment strategy will be used to safely evaluate the model's ability to capture true non-linear fraud patterns before fully replacing the rule engine.

### 2. Zero-Trust Security (Eliminating Pickle)
- **Current Limitation:** The API currently uses Python's `pickle` module to load the Random Forest and SHAP explainer. In fintech/enterprise security, `pickle` is banned due to severe Remote Code Execution (RCE) vulnerabilities.
- **Production Upgrade:** The model must be converted to **ONNX (Open Neural Network Exchange)** format and served via a hardened inference server like **NVIDIA Triton** or **AWS SageMaker**. This ensures execution in a sandboxed, language-agnostic environment.

### 3. Asynchronous Model Explainability (SHAP)
- **Current Limitation:** Computing exact SHAP values (`TreeExplainer`) synchronously on the main thread for every transaction is a massive CPU bottleneck. A flash sale generating 10,000 TPS would instantly crash the FastAPI event loop.
- **Production Upgrade:** Decoupling the architecture using an event-driven model (e.g., **Kafka + Celery**). The core `/evaluate` endpoint will return the risk score in <10ms to prevent blocking the checkout flow. SHAP calculations will be pushed to a background queue, processed asynchronously, and saved to a database for the merchant to view later.

### 4. Merchant Workflows vs. Developer Tools
- **Current Limitation:** The Vue 3 dashboard is essentially an internal Admin/Developer Console. Real-world merchants will not manually paste JSON payloads to evaluate orders.
- **Production Upgrade:** The system will integrate natively with merchant platforms (Shopify, WooCommerce) via **Automated Webhooks** that silently flag or block orders in the background. The dashboard will pivot to a bulk-analytics view (CSV exports, risk distribution charts) rather than single-transaction debugging.
